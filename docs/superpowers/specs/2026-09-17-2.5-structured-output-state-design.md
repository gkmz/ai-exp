# 2.5 结构化输出与状态更新编码实践设计

## 目标

为 Agent 学习路线中的 `2.5 结构化输出与状态更新` 补齐 `[示例]` 类型的编码实践，让学习者亲手完成以下闭环：

1. 接收模型返回的 JSON 字符串；
2. 将 JSON 解析并校验为可信决策；
3. 由运行时根据决策生成新的不可变状态；
4. 用测试验证正常路径和失败路径。

本练习不调用真实 LLM，不引入工具执行循环，也不进入 2.6 的模型路由与降级内容。

## 技术方案

使用 Python 3.12、Pydantic 2 和标准库 `dataclasses`：

- Pydantic 负责校验模型输出的字段、动作白名单和参数结构；
- 冻结的 dataclass 表示运行时状态；
- 纯函数负责状态转换，不原地修改旧状态；
- `unittest` 提供可重复运行的验收案例，不增加新依赖。

Pydantic 能清晰展示“JSON 语法正确”和“业务结构可信”是两个不同层次，同时避免真实模型 API 带来的密钥、网络和输出波动。

## 文件结构

实践代码放在：

```text
05-agent/course/ch02-llm-decision/2.5-structured-output-state/
├── task.md
├── skeleton.py
├── mine.py
├── reference.py
├── test_mine.py
└── test_reference.py
```

- `task.md`：任务目标、步骤提示、验收标准和运行方式；
- `skeleton.py`：包含完整类型、函数签名和中文 TODO；
- `mine.py`：学习者工作文件，初始内容与骨架一致；
- `reference.py`：独立参考实现，学习者完成后再查看；
- `test_mine.py`：针对学习者实现的验收测试；
- `test_reference.py`：验证参考实现和测试契约一致。

同时更新笔记 `2.5 结构化输出与状态更新.md`，将现有完整实现改为编码引导，并通过相对于 `ai-exp` 根目录的路径引用实践目录。

## 核心接口

练习围绕四个公开函数展开：

```python
def parse_decision(raw: str) -> Decision: ...
def apply_decision(state: AgentState, decision: Decision) -> AgentState: ...
def process_model_output(state: AgentState, raw: str) -> AgentState: ...
def main() -> None: ...
```

- `parse_decision`：解析 JSON，并由 Pydantic 完成严格结构校验；
- `apply_decision`：把可信决策转换为新状态；
- `process_model_output`：串联解析与状态更新；
- `main`：演示一次 `tool_call` 和一次 `finish` 状态流转。

`Decision` 使用动作区分的联合类型：

- `tool_call` 必须包含非空 `tool_name` 和字典类型 `arguments`；
- `finish` 必须包含非空 `answer`；
- 两种动作都包含非空 `reason`；
- 所有模型均拒绝未声明字段。

`AgentState` 至少包含 `step`、`status`、`pending_tool` 和 `final_answer`。每次成功决策都将 `step` 加一，并返回新对象；旧状态保持不变。

## 状态转换

| 决策 | 新状态 |
|---|---|
| `tool_call` | `status="waiting_tool"`，记录 `pending_tool`，清空 `final_answer` |
| `finish` | `status="completed"`，清空 `pending_tool`，记录 `final_answer` |

模型不得直接提供或覆盖 `step`、`status` 等运行时字段。

## 错误处理与验收

测试先于参考实现编写，并覆盖：

1. 合法 `tool_call` 可被解析；
2. 合法 `finish` 可被解析；
3. 非法 JSON 被拒绝；
4. 缺少必填字段被拒绝；
5. 未知动作被拒绝；
6. 未声明字段被拒绝；
7. 动作专属参数错误被拒绝；
8. `tool_call` 正确更新状态且不修改旧对象；
9. `finish` 正确更新状态且不修改旧对象；
10. 端到端函数完成解析与更新。

参考实现测试必须全部通过。学习者首次运行 `test_mine.py` 时应因 TODO 尚未完成而失败；完成 `mine.py` 后应全部通过。

## 学习边界

- AI 负责提供任务、提示、骨架、测试和独立参考实现；
- AI 不替学习者补全 `mine.py` 的核心 TODO；
- 不连接模型 API，不实现重试、路由、降级或工具执行；
- 完成标准是学习者实现通过 `test_mine.py`，并补充笔记中的实践总结；
- 在上述标准达成前，不开始 2.6。
